# AGENTS — 3D-Scan NN

## Назначение

Сайт `https://3d-scan-nn.ru/`: лазерное 3D-сканирование и обмеры в Нижнем Новгороде и области; на сайте заявлен выезд до 500 км.
Цель развития — повышать видимость по целевым коммерческим запросам и количество подтверждённых целевых обращений и заказов с учётом выгодности работ.
Все направления остаются в рассмотрении; приоритет выбирать по проверенному спросу, выгоде и возможностям исполнителя, а не по предположению агента.

## Порядок чтения

1. `PROJECT_STATUS.md` — текущее состояние, разрешённый этап, следующий шаг.
2. `PROJECT.md` — существующее устройство сайта и описание публикации.
3. `docs/superpowers/plans/2026-09-22-seo-growth.md` — план роста, показатели и критерии завершения.
4. `docs/SEO_BASELINE.md` — исходные наблюдения и границы их достоверности; читать нужный раздел.

Для узкого вопроса сначала искать непосредственно в коде. Не перечитывать всю документацию без необходимости.
`PROJECT_STATUS.md` — единственный текущий статус; `PROJECT.md` — обзор; план — очередь действий; исходный аудит — датированный снимок. Не дублировать между ними журналы сессий.

## Устройство и ограничения

- Репозиторий: текущая папка `3d-scan-nn`, ветка на момент подготовки документов — `main`.
- Статика HTML/CSS/vanilla JavaScript; основная страница и её логика — `index.html`, политика — `privacy.html`.
- Изображения и шрифты — `assets/`; поисковые служебные файлы — `robots.txt`, `sitemap.xml`; домен — `CNAME`.
- У проекта нет `package.json` и штатной сборки. Проверка калькулятора: `node --test tests/calculator.test.cjs` (встроенные модули Node.js, без установки зависимостей и внешних запросов). Не выдумывать команды `npm test`/`npm build` и не устанавливать зависимости без разрешения.
- Сохранять существующие Formspree, Метрику, домен и размещение. Новый движок, интеграции и изменение структуры страниц сначала согласовать.
- По `PROJECT.md`, отправка `main` в существующий `origin` запускает публикацию GitHub Pages. Учитывать внешний эффект даже у изменений документации; перед публикацией перепроверять процедуру и результат.

## Разрешения и сохранность

- Перед правками: `git status --short --branch`, затем относящийся к задаче diff. Не перезаписывать чужие изменения; при пересечении остановиться.
- Прямое поручение создать документы разрешает эти документы. Наличие задачи в плане само по себе не разрешает менять сайт или выполнять следующий этап.
- «Делай» и смысловой эквивалент разрешают согласованные локальные правки и безопасные проверки. Фиксация в Git, отправка в GitHub и публикация требуют явного разрешения по глобальным правилам пользователя; повторно уже выданное разрешение не спрашивать.
- Не отправлять тестовые заявки, сообщения, файлы клиентов и не менять настройки внешних кабинетов без соответствующего разрешения. Для проверки доставки заявки заранее согласовать конкретный тест, а затем проверить получение, а не только ответ HTTP.
- Не обращаться к `second-brain`, секретам и внешним папкам без отдельной необходимости и разрешения. Не хранить в репозитории доступы, персональные данные заявителей и необезличенные выгрузки: документы репозитория потенциально могут быть публичными.
- Не запускать агентов параллельно в одной рабочей папке. Отдельный clone/worktree — только после согласования с пользователем.

## Правила продвижения

- Разделять факт, вывод и гипотезу. Указывать дату, источник, регион, поисковик и устройство там, где они влияют на измерение.
- Не обещать первое место или сроки выхода в топ. Не выдавать примерные запросы за исследованную частотность, а ручную проверку выдачи — за устойчивую позицию.
- Не выдумывать кейсы, клиентов, отзывы, адреса, квалификацию, сроки, цены и точность. Публичные утверждения подтверждает владелец; иллюстрации не выдавать за выполненные работы.
- Не использовать накрутки, покупные отзывы, массовые ссылочные схемы, скрытый текст и страницы с одной заменой города или ключевой фразы.
- Клик по телефону/мессенджеру не равен обращению. Событие успешной формы не доказывает доставку владельцу. Обращение не равно оплаченному заказу.
- Не включать личные данные и содержимое заявок в параметры аналитики. Для локальных проверок использовать подмену отправки и счётчика, а не рабочие сервисы.

## Проверка результата

- Документы: корректные относительные ссылки, согласованные статусы, отсутствие секретов и `git diff --check`.
- Код сайта: проверка затронутого поведения, ссылок и формы без внешней отправки; снимки обычного и мобильного экранов при изменении вёрстки.
- Цены: согласованные владельцем ожидаемые суммы, граничные площади и скидки, согласованность текста и калькулятора; непредусмотренное снижение цены при росте площади недопустимо.
- SEO: доступный HTML, уникальные `title`/описание/H1 по назначению страницы, canonical, внутренняя навигация, sitemap; текущую индексацию доказывать отдельно.
- Проверять только относящийся к задаче объём. Не писать тесты ради формальности и не считать непроведённые проверки успешными.
- После существенного согласованного этапа актуализировать `PROJECT_STATUS.md` в рамках поручения пользователя. Долговременную память не менять без прямой просьбы.
